# Princípios SOLID
Fundamentos teóricos e exemplos conceituais dos cinco princípios de design orientado a objetos do SOLID.

## Você escreve código que escala ou apenas código que funciona?
Se você busca criar softwares fáceis de manter, testar e evoluir, os princípios SOLID não são opcionais, são a base de uma engenharia de software sólida.

Eles ajudam a reduzir a dívida técnica e evitam que o sistema se torne um "emaranhado de fios" impossível de mexer sem quebrar algo.

Aqui está um resumo rápido do que cada letra significa:
- **S** | Single Responsibility (Responsabilidade Única): Uma classe deve ter apenas um motivo para mudar. **Uma classe, uma função.**
- **O** | Open/Closed (Aberto/Fechado): Extensível para novos comportamentos, mas fechado para modificações no código existente.
- **L** | Liskov Substitution (Substituição de Liskov): As subclasses devem poder substituir suas classes base sem quebrar a aplicação.
- **I** | Interface Segregation (Segregação de Interface): É melhor ter várias interfaces específicas do que uma única interface "faz-tudo".
- **D** | Dependency Inversion (Inversão de Dependência): Dependa de abstrações e não de implementações concretas.

> [!TIP]
> **Dica**
> 
> Dominar esses princípios vai muito além da sintaxe; trata-se de pensar na longevidade do seu projeto.
